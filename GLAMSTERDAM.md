# Glamsterdam integration branch

Not for upstream. This branch is a superset used to test the Glamsterdam RPC surface end to end
before its pieces are landable: it pins a devnet go-ethereum, hardcodes post-Amsterdam
expectations in testgen, and carries one deliberate speccheck failure. Rebase and refresh it as
upstream changes land; do not open it as a PR.

## Start here

The work is spread over four places:

| Where | What |
|---|---|
| [ethereum/hive#1589](https://github.com/ethereum/hive/pull/1589) | generates the Amsterdam test chain and wires the clients; draft |
| this branch | pins a geth to match, regenerates the chain, refills every fixture |
| [execution-apis#855](https://github.com/ethereum/execution-apis/pull/855) | the callTracer spec on its own, without the Glamsterdam pieces; draft |
| [execution-specs#3261](https://github.com/ethereum/execution-specs/issues/3261) | the EIP-7928 disagreement this surfaced, and the missing test coverage |

Everything below is independently checkable, cheapest first. Each rung stands on its own, so you
can stop at whichever one answers your question.

**1. Build the chain** (~10 min, needs Go, no Docker). Confirms the chain is what it claims:

```sh
git clone -b glamsterdam-hivechain-prereqs https://github.com/MysticRyuujin/hive
cd hive && go run ./cmd/hivechain generate -outdir /tmp/chainA \
  -length 60 -tx-count 4 -tx-interval 1 -fork-interval 3 -lastfork amsterdam \
  -outputs genesis,chain,forkenv,headstate,txinfo,accounts,headfcu
jq .HIVE_AMSTERDAM_TIMESTAMP /tmp/chainA/forkenv.json   # 570 => activation at block 57
jq '.["tx-calltree"]|length' /tmp/chainA/txinfo.json    # calltree coverage
```

**2. Reproduce the fixtures** (~20 min). Checkout this branch, then follow *Refreshing* below.
`make fill` must report zero failures and `make test` exactly one (see *Known failures*). If your
fixtures differ from the committed ones, the geth pin moved — reconcile before drawing
conclusions.

**3. Replay against geth** (~20 min, needs Docker). The main claim, **252 tests / 0 failed**. See
*Running it*. Build the hive binary from the repo root, not `cmd/hive`:

```sh
go build -o /tmp/hive-bin .
/tmp/hive-bin --sim ethereum/rpc-compat --client-file clients-devnet7.yaml --client go-ethereum
```

**4. Run the cross-client matrix** (~15 min). Add besu, Nethermind and reth — they import the chain
and run the full suite with divergences, against go-ethereum's 252/252. Erigon still fails to
launch (erigontech/erigon#22896) and ethrex is excluded entirely, for the reason under *Known
failures*. Per-client totals matter more than the aggregate: a client that fails to launch shows
`total=1`.

**5. Read a divergence properly.** A failure means "differs from a geth-generated fixture", not
"the client is wrong" — see *Adjudicating divergences* below before reporting anything as a client
bug. Response diffs are in the simulator log as `response differs from expected (-- client, ++
test)`; client-side rejections are in `workspace/logs/<client>/client-*.log`, not the simulator
output.

**6. Check a client against the official BAL vectors** (~45 min). Useful for separating "this
client mis-implements EIP-7928" from "this chain or fixture is unusual" — Erigon scored 1013/1013
and besu 1012/1013 on the devnet-7 BAL suite. Recipe in *Running the EEST BAL vectors* below.

## Traps that will cost you time

- **`--sim.limit` needs the suite prefix for rpc-compat** (`rpc-compat/eth_config`, not
  `eth_config`), and for the `eels/consume-*` simulators it did not work at all — every pattern
  selected 0 of 316,484 tests while hive reported `tests=0 failed=0` and **exit 0**. Always
  assert `tests > 0`; a green run that ran nothing looks identical to success.
- **Use the devnet-7 images, not hive's defaults.** hive's defaults are release/master builds. The
  images are listed in `ethpandaops/glamsterdam-devnets` at
  `ansible/inventories/devnet-7/group_vars/all/images.yaml`; note they are sometimes *older* than
  hive's defaults.
- **The geth pin moves.** `glamsterdam-devnet-7` is rewritten often. Fixtures must be generated by
  the same commit hive builds, or a comparison means nothing. Read the commit back from a run's
  `clientVersions` and reconcile against `tools/go.mod`.
- **A client that fails to launch drops its tests silently** rather than failing them, so its total
  falls to 1 (`client launch`). Check per-client totals, not just the aggregate.
- **`workspace/logs/<client>/` keeps old logs.** Always take the newest by mtime.

## Refreshing after the devnet geth moves

The `glamsterdam-devnet-7` branch is rewritten often — it moved mid-session once already — and
the fixtures must be generated by the same commit hive runs, or the comparison is meaningless.

```sh
# 1. the geth commit hive will build (or read it back from a run's clientVersions)
git ls-remote https://github.com/ethereum/go-ethereum glamsterdam-devnet-7

# 2. pin the toolchain to it (a version bump, never a `replace`)
cd tools && go get github.com/ethereum/go-ethereum@<sha> && go mod tidy && cd ..
make -C tools build geth

# 3. rebuild hivechain from the hive branch carrying the Glamsterdam generator
go build -C <hive> -o $PWD/tools/hivechain ./cmd/hivechain

# 4. regenerate the chain, then refill every fixture
cd tools && ./mkchain.sh && cd .. && make fill && make test && make lint
```

Expect a whole-tree fixture diff: the block hashes change, so this is one of the few times the
usual "revert unrelated fixture drift" rule does not apply. `make fill` must report zero
failures; `make test` has exactly one known failure, below.

Sanity checks after regenerating:

- `tools/chain/forkenv.json` has `HIVE_AMSTERDAM_TIMESTAMP` (570 at the current parameters)
- `tools/chain/txinfo.json` lists `tx-calltree` and `tx-callrevert`, including a post-fork block
- blocks past the activation block still carry transactions

## Running it

Stage the fixtures into hive's rpc-compat simulator and build the client from the same geth
commit as the pin — never the prebuilt upstream image:

```sh
cp -R tests openrpc.json <hive>/simulators/ethereum/rpc-compat/
# uncomment the two ADD lines in that simulator's Dockerfile (local-only, do not commit)
```

```yaml
# clients-devnet7.yaml — devnet images are listed in ethpandaops/glamsterdam-devnets
# at ansible/inventories/devnet-7/group_vars/all/images.yaml
- client: go-ethereum
  dockerfile: git
  build_args: {github: ethereum/go-ethereum, tag: glamsterdam-devnet-7}
- client: besu
  build_args: {baseimage: ethpandaops/besu, tag: glamsterdam-devnet-7-caa5abf}
```

Always confirm `tests > 0` and that each client actually launched — a client that fails to start
drops its tests silently rather than failing them.

## Running the EEST BAL vectors

To check a client against the official EIP-7928 vectors rather than against these fixtures. Note
the fixture releases live on `ethereum/execution-specs`; `ethereum/execution-spec-tests` is
archived and read-only.

Build once against the release URL so the image caches the fixtures (842 MB):

```sh
/tmp/hive-bin --sim ethereum/eels/consume-engine --client-file clients-devnet7.yaml \
  --client go-ethereum --sim.buildarg \
  'fixtures=https://github.com/ethereum/execution-specs/releases/download/tests-glamsterdam-devnet%40v7.2.1/fixtures_glamsterdam-devnet.tar.gz'
```

Since `--sim.limit` does not filter these simulators, narrow the run by staging a filtered fixture
set instead. Inside the built image, reduce `.meta/index.json`'s `test_cases` to the ids you want
**and the matching `format`**, copy only their `json_path` files, and re-tar preserving the
`fixtures/` prefix — the 1013 BAL `blockchain_test_engine` cases come to 167 files and 3.3 MB:

```sh
docker run --rm -v "$PWD/out:/out" --entrypoint sh \
  hive/simulators/ethereum/eels/consume-engine:latest -c '...filter and tar to /out...'
cp out/fixtures.tar.gz <hive>/simulators/ethereum/eels/consume-engine/
/tmp/hive-bin --sim ethereum/eels/consume-engine --sim.buildarg fixtures=/fixtures \
  --sim.parallelism 4 --client-file clients-devnet7.yaml --client besu,erigon
```

The entrypoint only extracts `fixtures/.meta` and `fixtures/blockchain_tests_engine`, so keep that
layout. Throughput is roughly one test per second at `--sim.parallelism 4`.

## Known failures

`eth_simulateV1/two-blocks-with-complete-eth-sends` fails speccheck. Post-Amsterdam a
21000-gas transfer to a never-written account runs out of gas, and geth reports that as
`{-32015, "out of gas"}` while `src/schemas/execute.yaml` requires `-32015` messages to match
`^vm execution error.*`. The schema's own description says messages are suggestions and only
codes are enforced, so the pattern looks over-constrained — a standards decision for the
error-code work in #784, not something to patch here.

Two clients cannot launch, for reasons unrelated to this branch: **Erigon** rejects
`engine_forkchoiceUpdatedV4` with `too many arguments, want at most 2` although the method takes
three parameters including `custodyColumns` (erigontech/erigon#22896), and **ethrex** fails header
validation with `Base fee per gas is incorrect`.

**ethrex is excluded from the matrix for now, and it has two independent problems.**

What stops it launching is the *same* bug as Erigon's: it rejects `engine_forkchoiceUpdatedV4`'s
third parameter, with `Invalid params: Expected 2 or 1 params` (lambdaclass/ethrex#7074). Because the simulator's
`client launch` test fails only when the client returns an *error* to that call — a `SYNCING`
status would pass — the launch is judged failed and no tests run.

Underneath that, `ethrex import` fails at **block 1** with `Base fee per gas is incorrect`, and
that one is by design rather than a defect: ethrex supports post-merge networks only
(lambdaclass/ethrex#5504, "We don't support pre merge forks"), and lambdaclass/ethrex#7055 is
deliberately making `base_fee_per_gas` a required header field for every fork it validates. This
chain has 26 pre-London blocks (London at block 27), so none of them can import. ethrex already
tracks the consequence for this exact suite in lambdaclass/ethrex#6954 — their CI pins
`rpc-compat` to an old execution-apis commit precisely because the shared fixture chain became
pre-merge.

It is not specific to this branch: the upstream test chain has the identical fork layout
(`londonBlock: 27`, `mergeNetsplitBlock: 36`), which is why ethrex fails most of the default
`rpc-compat` suite too — there it launches only because that chain's `headfcu.json` calls
`forkchoiceUpdatedV3`, whose two parameters it accepts, after which it serves a genesis-only
chain.

So the legitimate route to testing ethrex against this suite is a merged-from-genesis chain
(`hivechain -pos`, which schedules every pre-merge fork at block zero), not a change to ethrex.
That is a second fixture set with reduced coverage — no uncles, no pre-London blocks, no early
fork boundaries — rather than a reconfiguration of this one, which is why it is out of scope here.

Run the other clients explicitly rather than relying on ethrex failing harmlessly, since a launch
failure only shows up as `total=1` in the results.

An earlier revision produced an activation block only go-ethereum would accept. That was geth's
EIP-7997 handling — with the deterministic factory contract absent from state, devnet-7 geth
inserts it at the start of the first Amsterdam block, which no other client does, so the access
list and state root diverged. Fixed by seeding the contract in genesis, and expected to be gone
in geth by devnet-8. If you see an activation-block BAL or state-root mismatch again, check the
genesis alloc first. History in ethereum/execution-specs#3261.

## Adjudicating divergences

**The fixtures are generated from geth, so a failing test means "differs from geth", not "the
client is wrong".** geth is one implementation; the spec is the authority. Where several clients
agree against geth, geth is the more likely defect, and the fix is to correct geth (or the spec)
and regenerate — not to make peers match a geth-shaped fixture. Failures are the expected output
of this harness; the work is sorting them.

Sort each one into:

1. **client defect** — it disagrees with the spec and with its peers;
2. **fixture/geth defect** — peers agree with each other against geth; fix upstream, then refill;
3. **spec silent** — implementations differ and the spec does not say; needs a decision before any
   fixture can be authoritative.

The current run's divergences are dominated by bucket 3. Roughly 60–70 of each client's failures
are in `eth_simulateV1`, concentrated in the block-identity fields of simulated blocks (`hash`,
`stateRoot`, `parentHash`, `blockAccessListHash`, `size`). All three clients that run produce
*different* `blockAccessListHash` values from each other and from geth for the same simulated
block, so the access list of a simulated block appears to be pinned down nowhere. Resolving that
is an execution-apis question, and it is the next thing worth chasing. One concrete secondary
observation while looking: on `ethSimulate-blockhash-simple`, Nethermind reports the simulated
block's `gasUsed` as `0x0` while the call it contains used `0x4398`, which looks like bucket 1.
